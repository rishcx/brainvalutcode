### The parity test must change — this is the trickiest part of P0

`src/core/store/d1.test.ts:50` currently asserts `0001_init.sql` is byte-identical to
`schema.sql`. That cannot survive an `ALTER TABLE`. Replace it with a **semantic** test:

```ts
const MIGRATIONS_DIR = new URL("../../../migrations/", import.meta.url);

/** Every migration file, applied in filename order — exactly what production does. */
function applyMigrations(db: DatabaseSync): void {
  const names = readdirSync(MIGRATIONS_DIR).filter((n) => n.endsWith(".sql")).sort();
  for (const n of names) db.exec(readFileSync(new URL(n, MIGRATIONS_DIR), "utf8"));
}

/** Normalised CREATE statements for every table and index, ordered. */
function objectsOf(apply: (db: DatabaseSync) => void): string[] {
  const db = new DatabaseSync(":memory:");
  apply(db);
  const rows = db
    .prepare("SELECT type, name, sql FROM sqlite_master WHERE sql IS NOT NULL ORDER BY type, name")
    .all() as unknown as { type: string; name: string; sql: string }[];
  db.close();
  // ALTER TABLE ADD COLUMN and an inline column produce the same sqlite_master SQL text
  // apart from whitespace, so normalise it and compare.
  return rows.map((r) => `${r.type} ${r.name} :: ${r.sql.replace(/\s+/g, " ").trim()}`);
}

test("schema parity: migrations/ and src/core/store/schema.sql agree", () => {
  assert.deepEqual(
    objectsOf(applyMigrations),
    objectsOf((db) => db.exec(readFileSync(SCHEMA_URL, "utf8"))),
  );
});
```

If the two disagree only in column *ordering* inside `deadlines`, put the new columns
**last** in `schema.sql` — `ALTER TABLE ADD COLUMN` always appends, so that makes them
match. **Do not** weaken the test to make it pass.

Then update **both** `fakeD1()` helpers (`src/core/store/d1.test.ts` and

## 3. Store implementations

`SqliteStore` (`src/node/store/sqlite.ts`) is the reference; `D1Store`
(`src/core/store/d1.ts`) must behave identically. Follow the existing patterns in both
files exactly — the `marks(n)` helper, the row→domain mappers, `this.now()`.

Required behaviours:

- `upsertTask` — `INSERT … ON CONFLICT(id) DO UPDATE SET` every column except `id`,
  `created_date` and `first_date`, which never change after creation.
- `listTasks` — `dueDate` is an equality filter, `dueOnOrBefore` is `<=`; they are mutually
  exclusive (if both are given, `dueDate` wins). `status: []` returns `[]`.
- `setTaskStatus` — sets `status`, `done_at` and `updated_at`. Passing `null` for
  `doneAtIso` clears `done_at`.
- `rollOpenTasks(toDate, nowIso)` —
  `UPDATE tasks SET due_date = ?, roll_count = roll_count + 1, updated_at = ? WHERE status = 'open' AND due_date < ?`.
  Returns `changes`. **`first_date` is untouched** — that is the whole point of the column.
- `appendTurn` — plain insert. **Also enforce a per-peer cap**: after inserting, delete the
  oldest rows for that `(channel, peer, local_date)` beyond 200. A runaway loop must not
  fill D1.
- `turnsForDay` — `ORDER BY at, id` (chronological).
- `purgeTurnsBefore` — `DELETE FROM chat_turns WHERE local_date < ?`, returns `changes`.
- `listNoteIndex` — `SELECT path, sha, title, tokens FROM note_index ORDER BY path`.
  Deliberately no `excerpt`: the scan must stay small.
- `getNoteExcerpts([])` returns `[]` **without** issuing a query (an empty `IN ()` is a SQL
  syntax error). Same for `deleteNotes([])` → `0`.
- `upsertNote` — upsert on `path`.

`D1Store` must use `.bind(...).run()` / `.all()` as the existing methods do, and read
`meta.changes` for counts. Where several writes happen together, prefer `db.batch()` —
**D1 allows only 50 queries per Worker invocation**, a separate limit from the 50 fetch
subrequests.

## 4. `src/core/time.ts` — add, never modify

```ts
export interface LooseWhen {
  date: string;          // YYYY-MM-DD
  time: string | null;   // "HH:MM" local, or null when none was given
  relative: boolean;     // true when the date came from "tomorrow"/"next monday"/…
}

/** Day of week (0 = Sunday) for a YYYY-MM-DD local date. Pure calendar maths, no tz. */
export function localDayOfWeek(date: string): number;

/** "tomorrow 6pm", "next monday", "4 Oct 2026 18:30", "2026-10-04", "tonight". */
export function parseLooseWhen(text: string, tz: string, now: Date): LooseWhen | null;

/** time === null delegates to dueAtFromLocalDate(date, tz, hour). */
export function dueAtFromLocalDateTime(date: string, time: string | null, tz: string, hour: number): string;
```

`parseLooseWhen` rules:

- Resolve "today" from `localDateOf(now, tz)` — never the host clock.
- Day words: `today`, `tonight` (→ date = today, and if no explicit time, `time = "20:00"`),
  `tomorrow`, `day after tomorrow`, `next <weekday>`, a bare `<weekday>` (the next strictly
  future occurrence; "monday" on a Monday means next Monday).
- Absolute dates: reuse `parseLooseDate` unchanged. **`parseLooseDate` must not be edited** —
  its existing tests must keep passing, including the refusal of `01/10/2026`.
- Times, searched anywhere in the string: `6pm`, `6 pm`, `6:30pm`, `18:00`, `at 6` (→ 18:00
  only when a `pm`/evening word is present, otherwise 06:00 — **when ambiguous, prefer the
  next future instant of the two**), `noon` (12:00), `midnight` (00:00).
- No date and no time → `null`. A time but no date → today if that instant is still in the
  future, otherwise tomorrow.
- `localDayOfWeek` uses `Date.UTC(y, m-1, d)` arithmetic on the parsed fields, **never**
  `new Date().getDay()`.
