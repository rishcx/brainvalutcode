## 2. Reminder text (`reminders/message.ts`) - plain text, no markdown, <= 400 chars per item

```ts
export function reminderText(d: Deadline, r: Reminder, ctx: AgentContext): string;
export function reminderBatchText(items: { d: Deadline; r: Reminder }[], ctx: AgentContext): string;
```
- T-0 (`kind "0"` or `snooze:*`), chat: `⏰ Reminder: <title>\nDue now (15:05). You set it at 14:55.\nReply: done, snooze 10m, or snooze 1h`
  ("You set it at" = `r.createdAt` local time for `kind "0"`; omit for snooze; add ` on <date>` when not today).
- Early offset: `⏰ In 24 hours: <title> (Tue 22 Sep, 06:00)` (+ reply line). Date-only deadline: date without time.
- Non-chat T-0: `⏰ Due now: <title>` + ` (<repo or source>)` when `sourceRef` is a GitHub URL (owner/repo only).
- Title: `oneLine`, <= 120 chars; a title equal to `Reminder`/`default`/empty renders as `Reminder (no subject given)`.
- Batch (> 3 items): `⏰ 5 reminders` + `• 1. <title> (due 15:05)` lines + `Reply 'done 2' or 'snooze 2 10m'.`

## 3. Delivery (`reminders/deliver.ts`) - replaces `sweep` in the job

```ts
// Target is imported from agent/contract.ts (V3-0)
export function targetFor(d: Deadline, cfg: Config, enabled: ChannelId[]): Target | null;
// origin (if its channel is enabled and the peer is allowlisted) else defaultChannel's first allowlisted id; else
// the first enabled channel; null when none
export async function deliverDue(ctx: AgentContext): Promise<{ sent: number; failed: number; targets: string[] }>;
```
Algorithm: `dueReminders(now)` -> load distinct deadlines (in parallel) -> orphan/closed rows handled as today ->
group open ones by target -> per group: `claimReminders(ids, crypto.randomUUID(), now, now-5min)` (skip ids not won)
-> <= 3 items: one message each; > 3: one batch -> `ch.sendTo ?? ch.send` -> success: `finishReminder(id, claim,
{sentAt})` for every row in that message; failure: WhatsApp target -> retry once on `defaultChannel` if different
(delivery `fallback:<ch>`); else `finishReminder(..., {error})`; a row whose `attempts` reaches 3 is finished as sent
with delivery `error:gave-up`. After a success: persist that recipient's numbering (`persistListing(ctx, ds, target)`),
kv `last:reminder:<ch>:<peer>` = `{"ids":[...],"at":iso}`, `appendTurn` (assistant, the text), one trace row
(kind `reminder`, route `reminder`, intent = kind(s)). **Auto-close:** an explicit chat deadline (`source chat`,
`confidence 1`) whose `kind "0"` or `snooze:*` row was delivered -> `setDeadlineStatus(id, "done")`.
Keep `sweep()` exported and unchanged (legacy tests use it).

## 5. Engine and jobs

- `materialise`: (a) ignore kinds starting `snooze:` in the "category changed -> delete unsent" rule; (b) upsert only
  when the row is missing or its `fireAt` differs (no write for unchanged rows). `create.ts#createReminder` gains
  optional `origin?: Target` stored on the deadline.
- `jobs/reminders.ts`: `sweep:reminders` (everyMinutes 1) runs `deliverDue` only; returns
  `sent=<n> failed=<n> targets=<list|none>`.
- `jobs/reconcile.ts`: `export const reconcileReminders: JobSpec` = `reminders:reconcile`, everyMinutes 15:
  `materialiseAll` + daily trace purge; returns `materialised=<n> purged=<n>`.

## 6. Channels and numbering

- Telegram/WhatsApp gain `sendTo(peer, text)` (peer must be allowlisted, else throw `not allowlisted`) and
  `typing(peer)` (Telegram `sendChatAction` to that chat only; WhatsApp no-op). `send()` keeps its behaviour
  (loops `sendTo` over the allowlist). WhatsApp window/template logic moves into the per-peer path unchanged.
- `format.ts`: `persistListing(ctx, ds, who?)`, `formatStatus(ctx, who?)`; `tasks/service.ts`:
  `persistTaskListing(ctx, view, who?)`, `resolveListRef(ctx, n, who?)`, `replyTasks(ctx, who?)`,
  `replyAddTask(ctx, c, who?)`, `replyDrop(ctx, index, who?)`, `resolveDoneIndex(ctx, index, who?)`.
  With `who`: key `last:list:<channel>:<peer>`; reads fall back to legacy `last:list` when the new key is absent.
  Without `who`: legacy behaviour (existing tests).

## Edge cases

- Two `deliverDue` calls in parallel on the same due rows -> exactly one message (claim).
- Target channel disabled / peer no longer allowlisted -> default channel.
- One of 3 messages to a peer fails -> only its rows are released; the others are sent.
- `deliverDue` with no channels -> no-op, rows untouched.
- A snoozed reminder in quiet hours fires anyway (user chose the time).
- Batch numbering persisted per recipient; a Telegram reminder never renumbers WhatsApp's list.
- A trace write failure never blocks delivery.

## Security

Redact every trace text field. `sendTo` refuses non-allowlisted peers. The admin route uses constant-time compare
and never returns more than 200 rows; no prompts are stored.
